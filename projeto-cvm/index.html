O que entra no pipeline

Toda companhia aberta entrega à CVM (Comissão de Valores Mobiliários), uma vez por ano, as demonstrações financeiras do exercício anterior. A CVM reúne essas entregas em pacotes anuais e os disponibiliza para download direto, sem cadastro. Hoje o pipeline processa três desses pacotes.

DRE — Demonstração do Resultado do Exercício

Receitas, custos, despesas e lucro. Fluxo de um período — tem data de início e de fim do exercício. É a demonstração que responde quanto a empresa ganhou ou perdeu.

Bronze: 101_dre_dfp — 428.532 registros   Silver: 201_dre_dfp — 163.013 registros, 24 colunas

BPA — Balanço Patrimonial Ativo

Bens e direitos da companhia num ponto no tempo. Snapshot de posição — sem data de início. É por isso que o DDL da BPA não tem a coluna DT_INI_EXERC: diferença sutil que o pipeline trata.

Bronze: 102_bpa_dfp — 815.877 registros   Silver: 202_bpa_dfp — 309.246 registros

BPP — Balanço Patrimonial Passivo

Obrigações e patrimônio líquido. Complemento do ativo — juntos, BPA e BPP formam o balanço completo. Mesma estrutura do BPA, mesma lógica de processamento.

Bronze: 103_bpp_dfp — 1.394.995 registros   Silver: 203_bpp_dfp — 528.874 registros

A CVM publica mais três demonstrações (DFC, DVA, DMPL). A estrutura modular do pipeline as acomoda sem mudança de arquitetura — seguiriam a numeração 104/204, 105/205, 106/206.

Arquitetura medalhão

O dado passa por quatro estágios, cada um com papel definido. O que entra bruto no primeiro sai tipado, normalizado e enriquecido no terceiro — pronto para análise sem que o consumidor precise saber de onde veio ou como foi limpo.

CVM→ Landing Zone→ Bronze→ Silver→ Gold→ Consumo
Landing Zone — preservação dos arquivos originais

Os ZIPs originais ficam em Unity Catalog Volumes, cada um com um _metadata.json gravando o Last-Modified HTTP da origem. Versões anteriores vão para archive/ com carimbo de tempo antes de qualquer sobrescrita.

Uma rotina diária faz requisição HEAD por exercício — compara com os metadados locais e só baixa o que mudou. Os notebooks de processamento nunca fazem chamada de rede à CVM.

Bronze — dado bruto com rastreio completo

Preserva a estrutura original da CVM sem nenhuma transformação. Cada ingestão adiciona quatro colunas de rastreio e grava em append-only. Nenhuma versão publicada pela CVM é apagada.

df_bronze = df_validado \
    .withColumn("_versao_ingestao", lit(versao_atual)) \
    .withColumn("_last_modified_cvm", lit(last_modified_cvm)) \
    .withColumn("_ingest_ts", current_timestamp()) \
    .withColumn("_source_file", lit(f"dfp_cia_aberta_DRE_con_{ano}.csv"))

Idempotência via controle_ingestao: mesma versão CVM processada duas vezes não gera duplicata — o notebook verifica fonte + ano + last_modified + status antes de processar.

Silver — dado padronizado e enriquecido

Window Function seleciona a versão mais recente da Bronze. Tipos são convertidos, a escala monetária é normalizada, e cinco colunas hierárquicas são derivadas da estrutura contábil. Gravação atômica via REPLACE WHERE.

df_silver.write \
    .format("delta") \
    .mode("overwrite") \
    .option("replaceWhere", f"ANO = {ano}") \
    .saveAsTable(f"{SCHEMA_SILVER}.201_dre_dfp")

A partição inteira é substituída numa operação atômica — ou tudo muda ou nada muda. Elimina a janela de vulnerabilidade que existia no antigo DELETE+APPEND.

Como o versionamento funciona na prática

A Bronze grava cada versão com _versao_ingestao crescente. A Silver aplica:

window_spec = Window.partitionBy(
    "CNPJ_CIA", "DT_REFER", "CD_CONTA", "ORDEM_EXERC"
).orderBy(col("_versao_ingestao").desc())

df_versao_atual = df_bronze \
    .withColumn("_row_num", row_number().over(window_spec)) \
    .filter(col("_row_num") == 1)

Resultado: a Silver sempre tem o valor mais recente, mas a Bronze preserva o histórico completo — é possível comparar a versão de março com a de julho.

3 · Estrutura hierárquica contábil

A CVM publica contas em hierarquia por notação de pontos: 3 → 3.01 → 3.01.01. O valor do pai é a soma dos filhos. Sem enriquecimento, o consumidor precisa remontar essa estrutura a cada consulta. A Silver deriva cinco colunas que tornam a hierarquia consultável diretamente.

As cinco colunas derivadas na Silver

NIVEL_CONTA — profundidade na hierarquia (1 a 5), derivado da contagem de pontos no código.

CD_CONTA_PAI — conta pai: tudo antes do último ponto. 3.01.01 → 3.01. NULL para nível 1.

CD_CONTA_RAIZ — primeiro segmento: 3.01.01 → 3.

TIPO_CONTA — totalizadora (até 2 níveis) ou analítica (3+ níveis). Dashboard deve filtrar por nível para evitar double-counting.

TIPO_ESTRUTURAL — aditiva (pai = soma dos filhos) ou derivada (contas como 3.02, 3.03 que são calculadas). Diferença relevante para validações contábeis.

qualidade

Guardrails e observabilidade

Os guardrails validam antes de modificar qualquer tabela. Se a validação falha, os dados ficam intactos. Cada verificação é registrada com UUID na tabela de observabilidade.

O que acontece quando um arquivo chega com problema interativo
✓Arquivo existe — ZIP encontrado na Landing Zone
✓Arquivo não vazio — CSV tem registros
✓Schema válido — todas as 15 colunas essenciais presentes
✓Contagem reconcilia — extração = Spark = validação = gravação
✓Gravação — dados escritos na tabela Delta
Quatro tabelas de observabilidade

controle_ingestao — cada ingestão fonte/ano, com last_modified_cvm e status. É a base para detecção inteligente de anos pendentes.

observabilidade_execucoes — cada execução de notebook, com job_id, run_id, task_key, duração e contagem de registros.

observabilidade_guardrails — cada verificação de guardrail, com tipo de check, resultado (PASS/FAIL/WARN) e detalhes.

observabilidade_jobs — cada run de job via MERGE idempotente: a primeira task grava o início, a última atualiza o fim. Status monotônico — uma vez ERROR, sempre ERROR.

Reconciliação em quatro pontos (Bronze)

A Bronze verifica a contagem em quatro momentos do pipeline e para se qualquer deles divergir:

count_extraido = len(df_pandas)           # 1. extração do CSV
count_spark    = df_raw.count()            # 2. conversão para Spark
count_validado = df_validado.count()       # 3. pós-validação de schema
count_tabela   = spark.table(...).count()  # 4. pós-gravação na Delta

Se o número muda entre dois pontos, o guardrail registra a divergência e interrompe o processamento daquele ano — sem afetar os demais.

Detecção inteligente de anos pendentes

Antes de processar, o pipeline consolida o que está pendente em seis fontes (três Bronze + três Silver), cruzando com a tabela de controle. O resultado é a lista ANOS_PROCESSAR — filtrada pela janela temporal relevante (últimos 5 anos).

Prioridade de override: widget Databricks → variável de ambiente → detecção inteligente → fallback (ano atual). Se CARGA=completa, todos os anos disponíveis são forçados.

infraestrutura

Infraestrutura como código

Três ambientes

ambientes.json declara dev, test e prod com composição dinâmica de schemas. Fora do Databricks, o config degrada para dev sem quebrar pytest no CI.

Databricks Asset Bundles

Jobs, tasks, schedules e parâmetros em YAML versionado. Deploy via bundle deploy --target. Três targets: dev, test, prod.

CI no GitHub Actions

Dois workflows: CI (Ruff + pytest a cada push) e testes E2E (bundle deploy + pipeline real no Databricks, sob demanda).

Compatível com Serverless

APIs Python padrão direto com UC Volumes. Sem staging em /tmp, sem dbutils.fs obrigatório. Funciona em Spark Connect.

Composição de schemas (ambientes.json) 
{
  "composicao": { "schema": "{prefixo}_{ordem}_{camada}" },
  "ambientes": {
    "dev":  { "prefixo": "proj_cvm_dev",  "existe": true  },
    "test": { "prefixo": "proj_cvm_test", "existe": true  },
    "prod": { "prefixo": "proj_cvm_prod", "existe": false }
  }
}
// dev  → workspace.proj_cvm_dev_01_bronze.101_dre_dfp
// test → workspace.proj_cvm_test_01_bronze.101_dre_dfp

Prod está declarado mas não instanciado (existe: false). O config recusa com mensagem explícita. Sem consumidor real, prod separado seria over-engineering — mas a arquitetura comporta sem mudança de código.
